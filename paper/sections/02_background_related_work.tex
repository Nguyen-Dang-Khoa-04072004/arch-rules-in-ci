\section{Related Work}\label{sec:background}

\subsection{Architectural Conformancbackground
Software architecture captures the key design decisions that shape a
system's structure and long-term evolution~\cite{bass2012,perry1992}.
As requirements change and development progresses, the implementation
may gradually diverge from the intended architecture. This divergence,
known as \emph{architecture erosion}, can lead to unauthorized
dependencies, cyclic dependencies, and layering violations, which
have been associated with declining maintainability and increasing
costs of change~\cite{perry1992,desilva2012,li2015,passos2010}.

Architecture conformance checking addresses this problem by comparing
the implemented structure against prescribed architectural
constraints~\cite{murphy1995,passos2010}. However, detecting violations
does not necessarily ensure that they are addressed. Prior studies
report that conformance tools are often underused and that detected
violations frequently remain unresolved~\cite{passos2010,pinto2017}.
Integrating conformance checks into continuous integration (CI) offers
one way to make architectural verification part of routine development
rather than an occasional activity~\cite{pinto2017,dirocco2024}.
Related work on continuous conformance further explores incremental
and non-blocking assessment of architectural alignment
~\cite{dirocco2024,santos2023}.

For our study, the key question is how architectural constraints are
encoded as executable checks and maintained in software repositories.
We therefore focus on executable architecture rules that can be
evaluated automatically, rather than on conformance assessment in
general.

\subsection{Executable Architecture Rules and Tools}

Architectural fitness functions are automated checks that evaluate
selected structural or quality properties as a system evolves
~\cite{ford2017}. Architecture-as-Code (AaC) takes a related approach
by representing architectural intent in machine-processable artifacts
that can be incorporated into development processes
~\cite{pontillo2026icsa}. Executable architecture rules provide a
concrete way to express architectural constraints and check them
automatically as software changes.

Our study examines three tools that support executable architecture
rules in different programming ecosystems. ArchUnit targets Java and
the JVM, expressing architectural constraints as Java-based tests
over classes, packages, and annotations. Its rules can check dependency
direction, package layering, inheritance restrictions, and
annotation-based conventions. These checks can be executed through
Maven or Gradle test tasks~\cite{archunit}.

For Python, import-linter defines contracts that check dependencies
between modules and packages, including layering, forbidden imports,
and module independence~\cite{importlinter}. For JavaScript and
TypeScript, dependency-cruiser analyzes dependency relationships and
supports rules for detecting cyclic dependencies and restricting
disallowed dependencies~\cite{depcruise}.

Although the these tools differ in how rules are specified and
executed, they share a common purpose: to encode architectural
constraints in executable tests or configurations. Their presence
in a repository, however, does not by itself establish that the checks
are routinely executed in development or CI workflows. We therefore
examine both the constraints encoded by these rules and their
integration into development workflows.

\subsection{Rule Exemptions and Evolution}

Executable architecture rules can change as developers maintain
and evolve a repository. These changes do not all have the same
implications for architectural enforcement. Developers may revise
the constraint expressed by a rule, exempt violations that the rule
would otherwise report, or disable the rule altogether. We distinguish
these cases because they represent different changes to the behavior
of an architecture check.

In our study, we define \emph{rule rot} as the growth, across revisions
of a rule that remains executable, in the set of violations that its
stated constraint still matches but that explicit waivers suppress.
In other words, rule rot occurs when additional violations are exempted
while the rule continues to check the constraint. Changing the
constraint itself changes which violations the rule matches, whereas
removing, commenting out, or disabling the rule ends its active
enforcement. We do not treat these changes as equivalent to rule rot.

The tools provide different mechanisms for handling violations. 
ArchUnit supports FreezingArchRule, which records existing
violations so that subsequent runs can focus on newly introduced
violations, and \texttt{.ignoreDependency(...)} for excluding specified
dependencies~\cite{archunit}. In import-linter, the
\texttt{ignore\_imports} setting allows specified imports to be
excluded from contract evaluation~\cite{importlinter}. These mechanisms
provide ways to tolerate selected violations while retaining an
active rule.

Dependency-cruiser requires a different distinction. Its
\texttt{path} and \texttt{pathNot} conditions specify which
dependencies a rule matches, so they define the scope of the constraint
rather than exempting matched violations. Severity settings affect
how violations are reported and whether a rule remains active;
a rule disabled through a severity setting is therefore treated as
deactivated, not as an instance of rule rot~\cite{depcruise}.

These differences matter when we reconstruct rule histories.
In particular, our operationalization treats the first observed use
of \texttt{FreezingArchRule} as an observable rule-rot event because
it indicates that existing violations are being tolerated while the
rule remains executable. The presence of the wrapper alone does not
reveal the number of exempted violations; that quantity can only be
determined when the corresponding violation store is available.
The methodology section explains how we identify and classify
these events across repository histories.
