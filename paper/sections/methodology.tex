\section{Methodology}\label{sec:study_design}

\input{figures/fig1_pipeline.tex}

We organize our methodology into five phases, as illustrated in
Figure~\ref{fig:study-pipeline}. First, we identify candidate GitHub
repositories and apply a set of eligibility criteria to construct the
study corpus. Second, we examine GitHub Actions workflows to identify
evidence of architecture-checker invocation. Third, we extract and
classify executable rules from ArchUnit, import-linter, and
dependency-cruiser. Fourth, we reconstruct the histories of rule files
to identify changes that may weaken or disable their enforcement.
Finally, we examine source-level dependency violations around the
introduction of parseable ArchUnit constraints.

\subsection{Repository Discovery and Selection}

We use the GitHub Search API to identify repositories containing
configuration artifacts associated with ArchUnit, import-linter, or
dependency-cruiser. Our search configuration contains 28 initial
tool-specific queries: seven for ArchUnit, seven for import-linter,
and fourteen for dependency-cruiser. We expand these queries into
170 paginated or split search requests. The recorded crawl shards
were last written on October 17, 2026, and we completed the
repository screening on October 18, 2026. After deduplicating results within each tool, we obtain 15,542
tool-specific repository entries: 9,258 for ArchUnit, 3,108 for
import-linter, and 3,176 for dependency-cruiser. These entries
represent 15,447 distinct GitHub repositories because some
repositories contain configuration artifacts for more than one tool.

We then apply our eligibility criteria to remove forks, archived
repositories, templates or scaffolding projects, and repositories
with less than six months between their creation and latest push.
This screening removes 10,799 entries and leaves 4,743 eligible
tool-specific repository entries. We further exclude entries
associated with unavailable repositories, repositories without an
identifiable rule file, or repositories that we cannot clone.
These exclusions account for 422 entries: 392 without a rule file,
15 unavailable repositories, and 15 clone failures. After these exclusions, our comparison corpus contains 4,321
tool-specific repository entries from 4,300 distinct repositories.
The corpus comprises 2,422 ArchUnit entries, 826 import-linter
entries, and 1,073 dependency-cruiser entries. A repository can
contribute entries to multiple tool groups when it contains
configuration artifacts for more than one tool.

\subsection{CI Workflow Analysis}

After constructing the comparison corpus, we examine GitHub Actions workflows to identify evidence of architecture-checker integration into CI. For import-linter and dependency-cruiser, we identify configured invocation based on tool-specific command references in workflow definitions. Since ArchUnit does not provide a dedicated workflow command that we can identify in the same way, we use relevant Maven or Gradle build and test tasks as indicators of potential invocation. These indicators suggest that a workflow is configured to invoke the corresponding checker or may execute tasks capable of running ArchUnit tests, but do not confirm that architectural constraints are actually executed.
Then, we calculate invocation proportions using only tool-specific
repository entries with determinate workflow results. We exclude
unavailable results from the denominator. To
account for repositories that contribute entries to multiple tool
groups, we calculate 95\% confidence intervals using bootstrap
resampling at the repository level.

\subsection{Rule Extraction and Classification}

We next examine the rule files in the comparison corpus. We extract
11,098 rule files and parse them into a common construct schema.
We then classify each construct into one of seven categories as defined in Table~\ref{tab:rule_taxonomy}. 
To establish a consistent classification scheme across the three tools, 
we develop a predefined mapping based on API names and 
keywords using an initial set of 1,000 eligible entries 
from the interleaved pilot dataset, comprising 337 PyPI, 
334 Maven, and 329 npm entries. We then freeze this mapping 
and apply it to the remaining constructs. Sequentially, 
classification set contains 21,713 constructs, 
of which 18,812 are assigned to one of the seven 
categories. The remaining 2,901 constructs are 
left uncategorized and excluded from category-proportion 
calculations. We therefore calculate category-level 
percentages using the 18,812 classified constructs 
as the denominator. We also define the structural 
family as the combination of dependency and layering 
constraints.

Our taxonomy relies on a predefined mapping of API names 
and keywords that is applied consistently across the three 
tools. Although this approach provides a systematic basis 
for classifying constructs, we do not evaluate the 
resulting assignments against an independently annotated 
reference set. The category distributions should therefore 
be interpreted in the context of this automated 
classification approach.

\subsection{Rule-History Reconstruction}

After extracting the rule files, we reconstruct their 
histories by comparing Git revisions and parsing file 
contents before and after each change. This process 
yields 86,339 edits across 11,098 rule files. We 
classify each edit into one or more of six categories: 
\emph{disable}, \emph{exempt}, \emph{loosen}, 
\emph{tighten}, \emph{add}, and \emph{restructure}. 
These categories capture changes that remove rules 
from enforcement, introduce exceptions, modify 
constraint restrictiveness, add new rules, or 
otherwise modify rule files. We classify an edit as \emph{disable} when it indicates that 
a rule is removed from enforcement. Such as deleting or commenting
out a rule, introducing \texttt{@ArchIgnore}, turning off its severity,
or removing all rule content from a file. We use \emph{exempt}
for changes that introduce or expand exceptions to rule
enforcement. These include introducing \texttt{FreezingArchRule}
or \texttt{.freeze()}, adding an \texttt{ignore\_imports} entry,
and increasing dependency-cruiser exception or \texttt{pathNot}
entries. Our automated detector also assigns this class when
the number of \texttt{warn} or \texttt{info} severity settings
in a file increases. We classify a change as \emph{loosen} 
if it makes an existing constraint less restrictive, 
and as \emph{tighten} if it makes the constraint more 
restrictive. We use \emph{add} when a change introduces a new rule and
\emph{restructure} for remaining changes, including file edits
that do not alter the parsed rules.

We operationalize \emph{rule rot}, as defined in
Section~\ref{sec:background-related-work}, at the rule-file
level. Specifically, we identify the first observed edit in
each file's history that is classified as either
\emph{exempt} or \emph{disable}. Each rule file therefore
contributes at most one event to the primary survival analysis.
Our detector relies on automated signals derived from file
differences and file-level token counts rather than verifying
the semantic effect of each edit on individual constraints.
We consequently interpret these observations as candidate
rule-rot events rather than manually confirmed instances
of rule rot.

For the primary analysis, we use the Kaplan-Meier estimator
\cite{kaplan1958nonparametric} to estimate the 24-month
cumulative incidence of the first detected exemption or
disabling event. As supplementary analyses, we examine an
alternative event definition based on the first
\emph{loosen} or \emph{exempt} edit, excluding \emph{disable}.
We estimate the 24-month cumulative incidence for this
alternative endpoint using a separate Kaplan-Meier analysis.
We also fit a Cox proportional-hazards model using the same
event definition and time-to-event variable, with the
logarithms of file-level commit count and author count
as covariates. We calculate file-level commit counts and author counts
over each rule file's entire available history in the
cloned repository. These measures are therefore full-history
descriptors rather than baseline or time-varying covariates.
We calculate 95\% confidence intervals for both
Kaplan-Meier estimates using percentile bootstrap
resampling at the rule-file level with 1,000 replicates.
For each replicate, we resample rule files with replacement
and recompute the 24-month cumulative incidence. We derive
the confidence limits from the 2.5th and 97.5th percentiles
of the bootstrap estimates. Replicates for which the
24-month estimate cannot be calculated are excluded.

We also estimate the proportion of rule files with no
subsequent modifications using percentile bootstrap
resampling of file-level indicators, again with 1,000
replicates. For the supplementary Cox model, we calculate
95\% confidence intervals using the Wald method based on
the estimated coefficients and their standard errors.

\subsection{ArchUnit Adoption Evaluation}

We examine source-level dependency violations around the introduction of ArchUnit constraints. We operationalize ArchUnit adoption as the first observed commit that introduces at least one parseable ArchUnit rule. This definition captures the introduction of a constraint declaration rather than its actual execution. Our corpus contains 2,422 repositories with ArchUnit artifacts. We select repositories with at least 12 months of observable history before and after the introduction commit, yielding an initial cohort of 317 repositories.
To examine how violations evolve around rule introduction, we reconstruct source-level import graphs at historical snapshots and evaluate dependency and layering constraints that can be assessed using these graphs. This replay-based procedure measures detectable source-level violations without executing ArchUnit itself. Consequently, our analysis covers only the subset of ArchUnit constraints that can be translated into checks over the reconstructed import graphs.

Let \(V(t)\) denote the number of detected dependency and layering violations at month \(t\) relative to the introduction commit, where \(t=0\) represents the introduction commit and \(t=-1\) represents the preceding monthly snapshot. For our longitudinal analysis, we retain repositories with at least one evaluable constraint and observed violation counts at \(t=-1\), \(t=0\), and \(t=12\). This selection yields 141 repositories. We exclude repositories without evaluable dependency or layering constraints to avoid interpreting an empty set of checks as evidence of zero architectural violations.
We then examine violation trends within each repository using ordinary least squares (OLS). Specifically, we estimate separate linear trends over the pre-introduction period (\(t=-12,\ldots,-1\)) and the post-introduction period (\(t=1,\ldots,12\)), excluding the introduction snapshot at \(t=0\). We summarize the repository-specific slopes using an unweighted mean and calculate confidence intervals through bootstrap resampling at the repository level.

Our analysis is descriptive and focuses on repositories that introduce parseable ArchUnit constraints and satisfy the observation criteria. Since we do not use an untreated control group or a difference-in-differences design, we interpret the results as violation trends observed around rule introduction rather than as causal effects of ArchUnit adoption.
