\section{Study Design}\label{sec:study_design}

We study a large sample of open-source repositories spanning the JVM, Python, and JavaScript/TypeScript ecosystems. To ensure relevance and comparability, we exclude forks, archived repositories, template projects, and repositories with insufficient activity. We also filter out common architecture templates such as JHipster and Spring Modulith, which often include rule files as scaffold rather than project-specific governance. The final sample contains 4,000--6,000 non-template repositories with at least two contributors, at least six months of history, and at least one tag or release point. This funnel is shown in Table~\ref{tab:funnel} and the repository mining pipeline in Figure~\ref{fig:pipeline}.

The mining workflow has four stages. First, we query GitHub for candidate repositories and extract metadata, commit history, and file-level evolution. Second, we identify rule files using ecosystem-specific heuristics: ArchUnit test classes, import-linter configuration files, and dependency-cruiser configuration, including files such as ``archunit.properties'', ``.importlinter'', or ``dependency-cruiser.js''. Third, we normalize rule content into a canonical schema (see \texttt{schema/canonical\_rule.json}) to support cross-tool comparison. Fourth, we replay historical rule executions across 24 monthly snapshots from $t=-12$ to $t=+12$ around adoption events, enabling direct comparison of architecture states before and after enforcement.

The canonical rule schema is designed to abstract away tool-specific syntax while preserving the structural meaning of executable architecture constraints. Each record includes repository metadata, ecosystem, rule file path, rule type (layering, dependency, cycle, visibility, naming, annotation, custom), target modules or packages, enforcement mode, exemption policy, and temporal evolution fields. This abstraction allows us to compare rule intent across Java, Python, and JavaScript ecosystems and to compute features such as rule openness, strictness, and exemption growth.

The longitudinal analysis is designed around repeated historical execution. For each repository with an architecture rule set, we reconstruct the state of the project and its rule configuration at monthly intervals. We then execute the rule set against the snapshot source tree, collecting rule pass/fail outcomes and structural metrics such as dependency edges, package cycles, import violations, and smells. This procedure distinguishes between genuinely new architecture enforcement and the mere presence of dormant rule files. It also allows us to observe rule rot: the gradual accumulation of exceptions, ignored imports, or frozen rules that reduce enforcement effectiveness without necessarily removing the rule file itself.

The causal evaluation uses a staggered difference-in-differences framework based on Callaway and Sant'Anna~\cite{callaway2021}. We identify adoption cohorts by the first month in which a repository begins executing architecture checks in CI or contains a non-empty rule configuration with active enforcement. For each cohort, we estimate the average treatment effect on the treated (ATT) using coarsened exact matching and nearest-neighbor matching on pre-treatment architecture indicators, repository maturity, activity, and project size. This design addresses non-random selection into adoption while accounting for staggered treatment timing and heterogeneous effects across event time. The event-study analysis examines dynamic treatment effects from 12 months before to 12 months after adoption, allowing us to distinguish immediate effects from delayed or lagged changes in architectural quality.
